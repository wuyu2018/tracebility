# 类区块链轻量化数据防篡改——实施计划

> 基于《类区块链轻量化数据防篡改设计.md》的设计理念，结合项目当前架构，制定以下实施方案。

## 一、决策记录

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 链的范围 | **按批次独立成链** | 每个 ProductionBatch 自成一条链，互不干扰，验证粒度更细 |
| RSA 密钥策略 | **预生成 + 配置文件指定** | 生产环境可控，密钥文件通过配置加载 |
| 外部锚定 | **日志文件 + 定时备份** | 现阶段轻量实现，将每日最新 hash 写入独立日志文件并归档 |
| UPDATE 处理 | **CREATE 和 UPDATE 都生成区块** | 每次数据修改都记录变更，保留完整追溯能力 |

## 二、区块链链接结构

### 2.1 按批次独立成链

```
批次 #10086 的区块链：

  MaterialPurchase#1 ──→ MaterialPurchase#3 ──→ ...
         ↓                        ↓
    (batch_material_relation 关联到批次)
         ↓
  ProductionBatch#10086 (创世块)
         ↓
  Storage#5
         ↓
  Inspection#12
         ↓
  TransportSale#8
```

- **创世块**：每个 `ProductionBatch` 记录创建时生成链的第一个区块
- **原料采购块**：该批次关联的 `MaterialPurchase` 记录在创建时按时间顺序链接，最终指向 `ProductionBatch`
- **业务流转块**：`Storage` → `Inspection` → `TransportSale` 按时间顺序依次链接
- 验证时按 `batch_id` 查询整条链，从头开始重算哈希比对

### 2.2 区块数据结构

```
BlockchainLog:
  id              BIGINT          PK 自增
  batch_id        BIGINT          所属批次 ID，标识属于哪条链
  entity_type     VARCHAR(50)     操作对象类型（PRODUCTION_BATCH / MATERIAL_PURCHASE / STORAGE / INSPECTION / TRANSPORT_SALE）
  entity_id       BIGINT          操作对象 ID
  action          VARCHAR(20)     操作类型（CREATE / UPDATE）
  previous_hash   VARCHAR(128)    前一个区块的 SHA-256 哈希
  current_hash    VARCHAR(128)    本区块的 SHA-256 哈希
  data_snapshot   TEXT            JSON 格式的数据快照（创建或更新后的完整字段值）
  signature       VARCHAR(512)    服务器 RSA 私钥对 current_hash 的签名（Base64 编码）
  timestamp       DATETIME        区块生成时间
  operator_id     BIGINT          操作人 ID
```

### 2.3 哈希计算规则

```
current_hash = SHA256(
  entity_type + entity_id + action +
  previous_hash +
  data_snapshot (规范化的 JSON 字符串) +
  timestamp
)
```

- 使用 Java `SHA-256` 算法
- `data_snapshot` 写入前需对 JSON 字段排序（按 key 字典序），确保相同数据产生相同 hash
- `current_hash` 计算后，使用 RSA 私钥签名，得到 `signature`
- 验证时用公钥验证签名，然后重算 `current_hash` 比对

## 三、RSA 密钥管理

### 3.1 配置文件

```yaml
blockchain:
  rsa:
    private-key-path: ${user.dir}/certs/blockchain-private.pem
    public-key-path: ${user.dir}/certs/blockchain-public.pem
```

### 3.2 密钥生成命令

```bash
# 生成 2048 位 RSA 私钥
openssl genpkey -algorithm RSA -out certs/blockchain-private.pem -pkeyopt rsa_keygen_bits:2048

# 提取公钥
openssl pkey -in certs/blockchain-private.pem -pubout -out certs/blockchain-public.pem
```

### 3.3 密钥加载

- 应用启动时从配置路径加载 PEM 文件
- 私钥用于签名，公钥用于验证
- `GET /api/blockchain/public-key` 对外暴露公钥，供外部审计人员使用

## 四、外部锚定

### 4.1 定时任务：每日凌晨 3:00

1. 遍历所有活跃批次（`ProductionBatch.is_deleted = false`）
2. 对每个批次，查该链最新区块的 `current_hash`
3. 写入锚定日志文件：`logs/blockchain-anchor-{yyyy-MM-dd}.log`
4. 格式：`batch_id | current_hash | timestamp | 该行哈希签名`
5. 同时写入 `blockchain_anchor` 表持久化

### 4.2 审计流程

审计人员拿到归档的锚定日志文件后：
1. 在系统中调用 `GET /api/blockchain/verify?batchId={id}` 获取当前链完整性报告
2. 取当前链最新 hash，与日志文件中对应 batch_id 的历史锚定 hash 比对
3. 若一致 → 数据未被整体替换；若不一致 → 链已被篡改

## 五、验证接口

| 接口 | 功能 |
|------|------|
| `GET /api/blockchain/verify?batchId={id}` | 校验指定批次所在链的完整性，返回每个区块的校验结果 |
| `GET /api/blockchain/verify/all` | 校验所有批次链的完整性 |
| `GET /api/blockchain/logs?batchId={id}` | 查询指定批次的区块历史 |
| `GET /api/blockchain/public-key` | 获取 RSA 公钥 |

### 验证算法

```
1. 按 batch_id + timestamp ASC 获取所有区块
2. 从第一个区块开始遍历：
   a. 用公钥验证该区块的 signature ⇔ current_hash
   b. 用区块数据重算 current_hash，与存储的 current_hash 比对
   c. 检查 previous_hash 是否等于前一个区块的 current_hash
   d. 记录每个区块的校验结果（通过 / 失败 + 失败原因）
3. 返回完整性报告
```

核心方法：
```java
public class BlockchainService {
    String calculateHash(BlockchainLog block);        // 计算 current_hash
    String sign(String hash);                         // RSA 私钥签名
    boolean verifySignature(String hash, String signature); // RSA 公钥验签
    BlockchainLog appendBlock(String entityType, Long entityId, String action,
                              Long batchId, String dataJson, Long operatorId); // 追加区块
    IntegrityReport verifyChain(Long batchId);        // 校验整条链完整性
}
```

## 七、数据库变更

### 7.1 新增表：blockchain_log

```sql
CREATE TABLE blockchain_log (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    batch_id BIGINT NOT NULL COMMENT '所属批次ID',
    entity_type VARCHAR(50) NOT NULL COMMENT '操作对象类型',
    entity_id BIGINT NOT NULL COMMENT '操作对象ID',
    action VARCHAR(20) NOT NULL COMMENT '操作类型: CREATE/UPDATE',
    previous_hash VARCHAR(128) DEFAULT NULL COMMENT '前一个区块哈希',
    current_hash VARCHAR(128) NOT NULL COMMENT '本区块哈希',
    data_snapshot TEXT COMMENT '数据快照(JSON)',
    signature VARCHAR(512) NOT NULL COMMENT 'RSA签名',
    timestamp DATETIME NOT NULL COMMENT '区块生成时间',
    operator_id BIGINT DEFAULT NULL COMMENT '操作人ID',
    INDEX idx_batch_id (batch_id),
    INDEX idx_timestamp (timestamp)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='区块链日志表';
```

### 7.2 新增表：blockchain_anchor

```sql
CREATE TABLE blockchain_anchor (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    batch_id BIGINT NOT NULL COMMENT '所属批次ID',
    current_hash VARCHAR(128) NOT NULL COMMENT '锚定时的最新哈希',
    anchor_date DATE NOT NULL COMMENT '锚定日期',
    created_at DATETIME NOT NULL COMMENT '记录创建时间',
    INDEX idx_batch_date (batch_id, anchor_date)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='区块链锚定记录表';
```

## 八、防篡改能力矩阵

| 攻击场景 | 哈希链 | 数字签名 | 外部锚定 |
|---------|--------|---------|---------|
| 修改单条记录数据 | 阻断 ✓ | — | — |
| 修改记录+重算该条hash | 下游断路 ✓ | 签名不匹配 ✓ | — |
| 修改记录+重算hash+绕过签名 | — | — | 与锚定hash矛盾 ✓ |
| 整条链替换（重算hash+重签名） | — | — | 与历史锚定hash矛盾 ✓ |

## 九、注意事项

1. **性能**：每次 CREATE/UPDATE 多一次 hash 计算 + RSA 签名 + DB 写入，约增加 10-20ms 延迟，可接受
2. **事务**：`appendBlock` 应在业务方法的事务内执行，保证业务数据与区块数据原子性
3. **RSA 密钥安全**：私钥文件应设置严格文件权限，生产环境建议使用 HSM 或密钥管理服务
4. **日志文件轮转**：锚定日志文件需配置 logrotate 或定期归档，防止磁盘写满
5. **初始化顺序**：历史数据初始化时，需确保同一批次内的区块按实际业务时间排序正确
