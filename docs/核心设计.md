# 核心设计

提炼自 docs/ 目录下的设计文档，涵盖设计哲学、数据库设计、防篡改机制、监督日志四大模块。

---

## 一、设计哲学

### 1.1 核心矛盾：最高权限者不可信

系统的根本假设：**管理员拥有数据库的最高权限，能直接操作数据文件**。这意味着无法通过权限控制来阻止篡改——围墙再高，管钥匙的人也能翻过去。

对策不是建更高的墙，而是**让每一次篡改都会留下不可抹除的证据**。系统不需要阻止管理员修改数据（企业的正常运转需要这种灵活性），但必须确保任何修改都能被检测和证明。

> 不必绝对限制最高管理员对数据的修改，企业的运转或许还需要他的维持，在未造成大量伤害的时候，适当留情面，但危害到企业的生存，日志记录会说明一切。

### 1.2 信任的分层递进

不依赖任何单一机制。三层防线，层层递进，每层解决上一层被攻破后的安全问题：

| 防线 | 防什么 | 被攻破后 |
|------|--------|---------|
| **哈希链** | 修改单条记录而不留痕迹 | 攻破者可以重算后续所有哈希修复链条 |
| **数字签名** | 重算整条链的哈希来掩盖篡改 | 攻破者必须有私钥，但私钥存在服务器上 |
| **外部锚定** | 整条链被替换（重算全部哈希 + 用服务器私钥全部重签名） | 攻破者无法伪造已被外部存储的历史锚定值 |

每一层都假设上一层已经被攻破，再设计下一层。最终连整条链被替换都能被发现。

### 1.3 宽容与追责

系统对人有两条原则：
- **宽容**：不影响正常业务操作。管理员该改数据还是能改，该运维还是能运维。
- **追责**：但所有操作都是可审计的，一旦出事，证据链是完整的。

这是一个"信任但验证"的设计：给你做事的自由，但保留证明你做过什么的能力。

### 1.4 领域事件驱动审计

审计是业务的副产品，不是业务的一部分。通过 `@TransactionalEventListener` 将区块链写入与业务逻辑解耦：

```
业务操作 → 发布领域事件 → 事件监听器追加区块链区块
```

业务代码不关心审计，审计代码不侵入业务。两者在同一个事务中完成，但职责完全分离。

### 1.5 比防御更重要的是检测

不追求让系统"无法被攻破"（这往往以牺牲可用性为代价），而是追求"只要被攻破就一定能被发现"。数据防篡改的核心不是加锁，是加见证人。

## 二、数据库设计

### 2.1 数据关系原则

| 原则 | 说明 |
|------|------|
| **一对多（独占）** | 用外键 + `ON DELETE CASCADE` 实现级联删除 |
| **多对多（共享）** | 必须用中间表解耦，禁止级联删除 |
| **中间表只存关系** | 中间表字段仅含双方主键 + 关系属性（如 `is_hidden`），业务数据留在各自实体表 |
| **软删除放在关系上** | 若要"仅对特定产品隐藏原料"，标记加在中间表；全局软删除才放在实体表 |
| **关联关系由应用层显式维护** | 不存在自动映射，增删关系必须通过业务代码明确操作中间表 |
| **避免数据冗余** | 不在多张表中重复存储相同字段 |

### 2.2 删除语义

物理删除已全面禁止。所有删除均为软删除：

| 操作 | 机制 |
|------|------|
| 产品删除 | 设置 `is_deleted = true`，保留批次和防伪码，确保已售商品仍可扫码溯源 |
| 产品硬删除 | 仅当该产品无任何生产批次和防伪码关联时才允许物理清除 |
| 原料/采购删除 | 设置 `is_deleted = true`，已软删实体冻结（不再接受后续业务更新） |
| 关系解绑 | 通过中间表标记 `is_hidden`，不影响其他产品的引用 |

### 2.3 核心实体关系链

```
material ─→ material_purchase ─→ batch_material_relation
                                       │
                                       ▼
                                production_batch
                                ┌─────┴──────┐
                             storage    inspection
                                └─────┬──────┘
                              transport_sale
                                     │
                               security_code
                                     │
                                 complaint
```

### 2.4 表结构概览

| 表名 | 说明 | 关键字段 |
|------|------|---------|
| `product` | 产品 | name, specification, is_deleted, qr_code_url |
| `material` | 原料品种 | name (唯一), is_active |
| `product_material_relation` | 产品-原料可见性 | product_id, material_id, is_hidden |
| `material_purchase` | 原料采购批次 | material_id, batch_number, supplier_name, is_deleted |
| `production_batch` | 生产批次 | batch_number, product_id, is_deleted |
| `batch_material_relation` | 批次-采购关联 | 复合主键 (batch_id, material_purchase_id) |
| `storage` | 仓储记录 | batch_id, storage_time, outbound_time, quantity |
| `inspection` | 出厂检验 | batch_id, sample_name, sample_quantity |
| `transport_sale` | 储运销售 | batch_id, environment_temperature, product_temperature |
| `security_code` | 防伪码 | code (唯一), batch_id, status, scan_count, first_scan_time |
| `complaint` | 投诉 | security_code_id (外键关联防伪码) |
| `admin` | 管理员 | username (唯一), password (BCrypt) |
| `operation_log` | 操作日志 | operator, entity_type, entity_id, action, summary |
| `blockchain_log` | 区块链日志 | chain_type, previous_hash, current_hash, signature, data_snapshot |
| `blockchain_anchor` | 区块链锚定 | batch_id, current_hash, anchor_date |

### 2.5 设计要点

- **原料与产品解耦**：`material_purchase` 不再绑定 `product`，通过 `product_material_relation` 中间表控制可见性
- **投诉关联防伪码**：通过 `security_code_id` 外键关联，消除冗余字符串字段
- **批次关联采购**：`batch_material_relation` 使用复合主键，一个批次关联多个采购批次
- **所有子表从级联删除改为 RESTRICT**：由应用层 `DeletionPolicy` 统一控制删除逻辑

### 2.6 一次查询原则

防伪码首次扫描返回正品信息；后续扫描视为重复查询，返回伪品警示。基于 `SecurityCode.scanCount` 判断：

- `scanCount = 0` 或 `null`：未查询过
- `scanCount = 1`：首次查询，`valid: true`
- `scanCount > 1`：重复查询，`valid: false` + 伪品警告

## 三、区块链轻量化防篡改

### 3.1 双链架构

| 链 | 范围 | 覆盖实体 |
|----|------|---------|
| **MATERIAL 链** | 全局单链 | material, material_purchase 的创建/变更/删除 |
| **BATCH 链** | 每批次独立链 | production_batch → storage → inspection → transport_sale 全生命周期 |

两条链通过 `ref_master_chain_hash` 字段交叉关联：BATCH 链创世块记录创建时 MATERIAL 链的最新哈希值。

### 3.2 区块结构

表 `blockchain_log` 核心字段：

| 字段 | 说明 |
|------|------|
| `chain_type` | 链类型：MATERIAL / BATCH |
| `entity_type` | 实体类型（MATERIAL / STORAGE / INSPECTION 等） |
| `entity_id` | 对应实体记录的 ID |
| `action` | 仅 `CREATE` / `UPDATE`（物理删除已禁止） |
| `previous_hash` | 前一个区块的 SHA-256 哈希 |
| `current_hash` | 本区块的 SHA-256 哈希 |
| `data_snapshot` | 操作时的完整数据快照（JSON） |
| `signature` | current_hash 的 RSA-2048 签名（Base64） |
| `ref_master_chain_hash` | BATCH 链专用，引用 MATERIAL 链最新哈希 |

### 3.3 密码学机制

**SHA-256 哈希计算**（9 个字段用 `|` 拼接）：

```
current_hash = SHA-256(
    entityType + "|" + entityId + "|" + action + "|"
    + previousHash + "|" + dataSnapshot + "|"
    + timestamp + "|" + batchId + "|" + operatorId + "|"
    + refMasterChainHash
)
```

**RSA 数字签名**：
- 算法：SHA256withRSA
- 密钥：2048 位，支持 PEM 文件加载或自动生成
- 签名内容：`current_hash` 原始字节
- 输出：Base64 编码字符串
- 公钥通过 `GET /api/blockchain/public-key` 对外公开

### 3.4 写入方式（事件驱动）

```
领域事件 → @TransactionalEventListener(phase = AFTER_COMMIT) → BlockchainService.appendBlock()
```

| 事件 | 触发时机 | 链 | 实体类型 |
|------|---------|-----|---------|
| BatchCreated | 批次创建 | BATCH | PRODUCTION_BATCH |
| GoodsReceived | 入库完成 | BATCH | STORAGE |
| InspectionCompleted | 检验完成 | BATCH | INSPECTION |
| TransportSaleRecorded | 运输/销售记录 | BATCH | TRANSPORT_SALE |
| MaterialChanged | 物料变更 | MATERIAL | MATERIAL |
| MaterialPurchaseChanged | 采购变更 | MATERIAL | MATERIAL_PURCHASE |

### 3.5 哈希链的链接原理

```
区块1（首个）：
  input = "MATERIAL|1|CREATE||{"id":1,"name":"生牛乳"}|2026-05-10T10:00:00"
  previous_hash = (null → "")
  current_hash  = SHA-256(input) = "a1b2..."

区块2：
  input = "MATERIAL_PURCHASE|1|CREATE|a1b2...|{"id":1,...}|2026-05-10T10:05:00"
  previous_hash = "a1b2..."  ← 区块1的 current_hash
  current_hash  = SHA-256(input) = "c3d4..."

区块3：
  previous_hash = "c3d4..."  ← 区块2的 current_hash
  ...
```

每个区块的 `previous_hash` 就是前一个区块的 `current_hash`。修改任意区块 → 该区块 `current_hash` 改变 → 后续所有区块链断裂。

### 3.6 验证 API

| 端点 | 功能 |
|------|------|
| `GET /api/blockchain/verify/material` | 验证 MATERIAL 链完整性 |
| `GET /api/blockchain/verify/batch?batchId=X` | 验证指定 BATCH 链 |
| `GET /api/blockchain/verify/all` | 验证所有 BATCH 链 |
| `GET /api/blockchain/public-key` | 获取 RSA 公钥 |

验证规则：对每个区块依次检查：
1. **链式完整性**：第 i 块的 `previous_hash` == 第 i-1 块的 `current_hash`
2. **哈希一致性**：重算 `current_hash` 与存储值一致
3. **签名有效性**：用公钥验证 RSA 签名

### 3.7 初始化

`BlockchainInitializationService`（`CommandLineRunner`）在首次启动时自动检测，若无区块链数据则遍历所有历史业务记录重建完整链。幂等设计。

## 四、监督日志机制

### 4.1 三层日志体系

| 机制 | 存储位置 | 触发方式 | 防篡改 |
|------|---------|---------|--------|
| 操作日志 | `operation_log` 表 | `@OperationLog` AOP 注解 | 否（记录级，可删改） |
| 区块链日志 | `blockchain_log` 表 | `@TransactionalEventListener` | 是（SHA-256 + RSA） |
| 每日锚定 | `blockchain_anchor` 表 + 签名文件 | 定时任务（凌晨 3:00） | 是（RSA 签名） |

这三层对应设计哲学中的"宽容与追责"：
- 操作日志供日常管理查询（可删改，追求灵活）
- 区块链日志供防篡改验证（不可伪造，追求可信）
- 每日锚定供外部审计（独立于数据库的证据）

### 4.2 操作日志（operation_log）

通过 `@OperationLog` 注解自动记录：

```java
@OperationLog(entityType = "PRODUCT", action = "CREATE")
@PostMapping("/products")
```

| 字段 | 说明 |
|------|------|
| `operator` | 操作人用户名（从 JWT 提取） |
| `entity_type` | PRODUCT / MATERIAL / BATCH 等 |
| `entity_id` | 被操作记录 ID |
| `action` | CREATE / UPDATE / DELETE / LOGIN 等 |
| `summary` | 可读描述，如"创建产品 ID=3" |

覆盖接口：产品、原料、采购、批次、检验、仓储、运输、防伪码、投诉、管理员登录注册。

### 4.3 防伪码查询追踪

每次扫码触发状态变更，记录在 `security_code` 表：

```java
recordQueryAndActivateIfNeeded():
  - 首次查询：未激活 → 已激活，记录 first_scan_time，scanCount = 1
  - 重复查询：scanCount++
```

重复查询时返回伪品警示："该产品已被查询过 N 次，首次查询时间：XXX。重复查询可能是伪品，请谨慎购买！"

### 4.4 登录安全

基于 Redis 的登录防暴机制：

| 规则 | 参数 |
|------|------|
| 最大失败次数 | 5 次 |
| 锁定时间 | 30 分钟 |
| 失败记录过期 | 1 小时 |
| 计数范围 | 密码错误 + 验证码错误均计入 |

### 4.5 应用日志（SLF4J）

各模块使用统一前缀标识来源：

- `[产品管理]`、`[原材料管理]`、`[检验检测]`、`[仓储]`、`[运输销售]`、`[防伪码管理]`——数据管理
- `[管理员登录]`——认证
- `[投诉提交]`、`[投诉查询]`、`[投诉删除]`——投诉
- `[JWT 过滤器]`——安全
- `[BlockchainInit]`——区块链初始化
- `[V2 ...]`、`[Event]`、`[Blockchain]`——DDD 模块

## 五、DDD 演进

项目中存在两套并行的实现：V1（传统 CRUD 分层）和 V2（DDD 风格）。

V2 模式遵循：

```
domain/        领域实体 + 领域事件 + 值对象 + 仓储接口
application/   应用服务 + DTO + 事件监听器
interfaces/    REST 控制器 + 接口层 DTO
```

| 业务域 | V1 状态 | V2 状态 |
|--------|---------|---------|
| 批次创建/仓储/检验/运输销售 | 已覆盖 | 已覆盖（DDD） |
| 追溯查询 | 已覆盖 | 已覆盖（V2） |
| 物料品种/采购单 | 已覆盖 | 待迁移（第二阶段） |
| 防伪码/产品/投诉/认证 | 已覆盖 | 暂无 V2 计划 |
