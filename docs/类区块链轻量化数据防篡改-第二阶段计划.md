# 第二阶段计划：V2 应用服务完整覆盖，淘汰 V1 重复路径

## 一、动机

当前代码存在两套并存的服务层，相同业务两套实现，导致维护成本增加和区块链区块追加逻辑分散。第二阶段的目标：

1. **V1-V2 重叠业务**：删除 V1 实现，保留 V2（DDD 规范）
2. **V1 独有业务**：为 V2 补充缺失的 ApplicationService（物料品种、采购单），遵循现有 DDD 模式

## 二、V1 vs V2 覆盖现状

| 业务域 | V1 端点 | V2 端点 | 处理方式 |
|--------|---------|---------|---------|
| **创建批次** | `POST /api/batches` | `POST /api/v2/batches` | 删除 V1 |
| **仓储** | `POST /api/batches/{id}/storage` | `POST /api/v2/storage` | 删除 V1 |

## 三、执行步骤

### Step 1：创建 V2 MaterialApplicationService（物料品种）

遵循现有 V2 模式（以 `ProductionBatchApplicationService` 为模板），每次变更通过领域事件驱动区块链区块追加。

#### 新建文件

| 文件路径 | 说明 |
|----------|------|
| `traceability/domain/event/MaterialCreated.java` | 品种创建领域事件 |
| `traceability/domain/event/MaterialUpdated.java` | 品种更新领域事件（内容修改、激活/停用、软删均触发此事件） |
| `traceability/application/service/MaterialApplicationService.java` | 品种应用服务 |
| `traceability/application/dto/CreateMaterialRequest.java` | 创建请求 DTO（应用层） |
| `traceability/application/dto/UpdateMaterialRequest.java` | 更新请求 DTO（应用层） |
| `traceability/application/dto/MaterialResponse.java` | 响应 DTO（应用层） |
| `traceability/application/event/MaterialCreatedEventListener.java` | 监听 `MaterialCreated` → 调用 `blockchainService.appendMaterialChainBlock(...)` |
| `traceability/application/event/MaterialUpdatedEventListener.java` | 监听 `MaterialUpdated` → 调用 `blockchainService.appendMaterialChainBlock(...)` |
| `traceability/interfaces/rest/MaterialVarietyController.java` | `POST/GET/PUT/DELETE /api/v2/material-varieties` |
| `traceability/interfaces/dto/CreateMaterialVarietyRequest.java` | 接口层 DTO |
| `traceability/interfaces/dto/UpdateMaterialVarietyRequest.java` | 接口层 DTO |
| `traceability/interfaces/dto/MaterialVarietyResponse.java` | 接口层响应 |

#### MaterialApplicationService 方法

```
createMaterial(CreateMaterialRequest req) → MaterialResponse
    1. 检查 name 唯一性
    2. 创建 Material 实体并保存
    3. 发布 MaterialCreated 事件（afterCommit）
    4. 返回响应

updateMaterial(Long id, UpdateMaterialRequest req) → MaterialResponse
    1. 加载现有实体
    2. 检查 is_deleted，已软删则抛出 BusinessException（冻结规则）
    3. 更新字段（name / isActive，含 activate/deactivate）
    4. 保存
    5. 发布 MaterialUpdated 事件（afterCommit）
    6. 返回响应

deleteMaterial(Long id) → void
    1. 加载现有实体
    2. 执行软删（is_deleted = true）
    3. 保存
    4. 发布 MaterialUpdated 事件（afterCommit，data_snapshot 含 is_deleted: true）

listMaterials(Boolean activeOnly) → List<MaterialResponse>
getMaterial(Long id) → MaterialResponse
```

#### 事件监听器

```
MaterialCreatedEventListener.onMaterialCreated(MaterialCreated event):
    → 查库获取完整 data_snapshot（整条实体记录的 JSON 序列化，含 is_deleted: false）
    → blockchainService.appendMaterialChainBlock("MATERIAL", id, "CREATE", snapshot, null)
    
MaterialUpdatedEventListener.onMaterialUpdated(MaterialUpdated event):
    → 查库获取完整 data_snapshot（整条实体记录的 JSON 序列化）
    → 软删场景：snapshot 自动包含 is_deleted: true，无需额外 operation 字段（方案 A）
    → blockchainService.appendMaterialChainBlock("MATERIAL", id, "UPDATE", snapshot, null)
```

### Step 4：V2 接口层实现规范

每个 V2 控制器遵循以下结构：

```
追踪溯源码：
  GET /api/v2/trace/verify?code=XXX        ← TraceabilityQueryController
  GET /api/v2/trace/batch/{batchNumber}     ← TraceabilityQueryController

批次管理：
  POST /api/v2/batches                      ← ProductionBatchController

物料品种：
  POST   /api/v2/material-varieties          ← MaterialVarietyController
  GET    /api/v2/material-varieties          ← MaterialVarietyController
  GET    /api/v2/material-varieties/{id}     ← MaterialVarietyController
  PUT    /api/v2/material-varieties/{id}     ← MaterialVarietyController
  DELETE /api/v2/material-varieties/{id}     ← MaterialVarietyController（软删 → 触发 UPDATE 区块）
  POST   /api/v2/material-varieties/{id}/deactivate ← MaterialVarietyController（走 updateMaterial）
  POST   /api/v2/material-varieties/{id}/activate  ← MaterialVarietyController（走 updateMaterial）

采购单：
  POST   /api/v2/materials                   ← MaterialPurchaseController
  GET    /api/v2/materials                   ← MaterialPurchaseController
  GET    /api/v2/materials/{id}              ← MaterialPurchaseController
  PUT    /api/v2/materials/{id}              ← MaterialPurchaseController
  DELETE /api/v2/materials/{id}              ← MaterialPurchaseController（软删 → 触发 UPDATE 区块）

> 注：DELETE 端点对应软删操作，物理删除已全面禁止。软删触发 `"UPDATE"` 区块链区块，data_snapshot 含 `is_deleted: true`，无独立 `"DELETE"` action。

仓储/检验/运输销售：
  POST /api/v2/storage                      ← StorageController
  POST /api/v2/inspections                  ← InspectionController
  POST /api/v2/transport-sales              ← TransportSaleController
```

### 接口 DTO 结构

每个 Controller 接口 DTO 按以下模式：

```java
// interfaces/dto/ 包 — 用于 HTTP 序列化/反序列化
public class CreateMaterialVarietyRequest {
    // getters/setters
    public MaterialApplicationService.CreateMaterialRequest toAppRequest() { ... }
}

// application/dto/ 包 — 用于应用服务层
public record CreateMaterialRequest(String name) {}
```

### Step 5：删除 V1 区块链桥接代码

V1 的 `MaterialServiceImpl` 和 `MaterialPurchaseServiceImpl` 在 Step 3 中删除后，其中直接调用的 `BlockchainService.appendMaterialChainBlock()` 代码自然移除。

V2 事件监听器（MaterialCreatedEventListener / MaterialUpdatedEventListener / MaterialPurchaseCreatedEventListener / MaterialPurchaseUpdatedEventListener）接管区块链区块追加。

> V1 中 `deleteMaterial()` 和 `deleteMaterialPurchase()` 不触发区块链；V2 中这两个操作的软删动作会触发 UPDATE 事件并追加区块。V2 迁移后，区块链覆盖范围相比 V1 **扩大**到软删场景。
